2026-09-30 · Module 1

What is an identity? (first real session, not just setup)

  • A digital identity is four pieces: an entity (the real thing) plus identifiers (point to it), attributes (facts about it) and credentials (prove it). Nothing more exotic than that.
  • Two kinds of entity: human (interactive, can do MFA, eventually leaves) and non-human (automatic, can't do MFA, often outlives its creator). Machine identities now outnumber human ones by a wide margin, and get watched far less.
  • Identity became "the new perimeter" because the network edge stopped meaning anything once laptops, SaaS and cloud servers left the building — the one constant left in any access request is an identity asking for something.
  • The flip side: attackers don't break in any more, they log in.
  • The office-building analogy (entity=you, identifier=badge name, attributes=floor/department, credential=badge chip, reception=identity system) recurs through the whole course.

Core concepts the mental models

Anatomy of an identity

Entity (the real thing) → identifiers (email, employee ID) + attributes (department, role) + credentials (password, passkey, certificate).

Two kinds of entity: humans and non-humans (service accounts, keys, workloads, bots, agents). NHIs now far outnumber humans.

Module 1

IAAA: the four questions

  1. Identification: who do you claim to be?
  2. Authentication (AuthN): prove it.
  3. Authorization (AuthZ): what may you do?
  4. Audit: what did you do?

AuthN ≠ AuthZ. Many breaches are authorization failures (too much access), not authentication failures.

Module 2

Tokens are wristbands

After you authenticate, you get a session cookie or token. Whoever holds it is treated as you, skipping the password and MFA. Token theft is the modern bypass.

Module 2

Who talks to whom

  • User → machine: login; phishing is the threat.
  • User → user: mediated by systems; impersonation, BEC and deepfakes are the threats.
  • Machine → machine: API keys, certificates, tokens; leaked long-lived secrets are the threat.
  • Machine on behalf of a user: delegation; over-scoped consent is the threat.

Human-present test: no human means no MFA, so rely on short lifetimes, vaults, workload identity and scoping.

Module 3

Delegation vs impersonation

Delegation: "Sam on behalf of Priya", with both identities logged, scoped and revocable. Impersonation: Sam acts as Priya and accountability is lost. Always prefer delegation, for people and for agents.

Module 3

Classifying credentials

  • Shared secret (password, API key): both sides know it, so either can leak it.
  • Key pair (passkey, certificate): the private key never leaves; the server stores only the public key.
  • Bearer (cookie, API key): works for whoever holds it.
  • Proof-of-possession (passkey, DPoP, mTLS): signs a fresh challenge, so it can't be replayed.

Primary → derived: passkey → IdP session → assertion or token → app cookie. Stealing a derived credential skips MFA.

Module 4

MFA strength ladder

  1. SMS / voice: SIM swap, phishable
  2. TOTP app: phishable (relayed)
  3. Push: MFA fatigue (number matching helps)
  4. FIDO2 / passkeys / certificates: phishing-resistant

Passkeys are phishing-resistant because the key is bound to the website's origin; a look-alike domain gets nothing.

Module 5

Where MFA can't reach

  • Legacy protocols (IMAP, POP, basic SMTP, NTLM)
  • After login (stolen tokens)
  • Machine identities
  • Enrolment and recovery (help desk, attacker-registered methods)
  • Inside the Windows network after desktop logon

Module 5

Authorization models

  • ACL: list on each resource
  • RBAC: roles (watch for role explosion)
  • ABAC: attributes and context
  • ReBAC: relationships (Google Zanzibar)
  • PBAC: policy as code (AWS IAM, OPA, Cedar)

Principles: least privilege, separation of duties, just-in-time, zero standing privilege.

Module 6

Directories and sources of truth

AD (on-prem: LDAP, Kerberos, Group Policy) ≠ Entra ID (cloud: SAML, OIDC, OAuth). Most enterprises are hybrid, synced by Entra Connect. HR is the authoritative source for people; the directory consumes it.

Module 7

Lifecycle: Joiner, Mover, Leaver

Mover is where privilege creep is born (new access is added, old access never removed). Leaver failures create orphaned accounts. SCIM automates provisioning and deprovisioning. NHIs rarely have a leaver event at all.

Module 9

SSO in one picture

Apps (SP / RP) outsource authentication to one IdP and trust its signed statement. Sessions come in layers (device, IdP, app), so disabling a user in the IdP doesn't kill existing app sessions. SSO creates accounts just-in-time but can't remove them, which is why SCIM is needed. Prefer SP-initiated flows. The IdP is the master key.

Module 10

IAM vs IGA vs PAM vs CIAM

  • IAM: make access work (AuthN, AuthZ, SSO)
  • IGA: keep access right, and prove it (reviews, SoD, lifecycle)
  • PAM: control the dangerous accounts (vault, rotation, session recording, JIT)
  • CIAM: customers at scale (low friction, bots, account takeover, privacy)

Modules 13–15

PAM vs PIM

PAM asks how a privileged account's credential is protected every time it's used (vault, rotate, record the session). PIM asks who currently holds a privileged role and for how long — eligible vs. active, time-boxed activation with justification (Entra ID's own PIM feature is the clearest real example). PIM governs who can become privileged; PAM protects the credential once they do. Both aim at the same goal: zero standing privilege.

Module 14

Attackers think in graphs

Stages: recon → initial access → persistence → privilege escalation → lateral movement → objectives. Almost every step is an identity action. BloodHound maps the graph of relationships to Domain Admin.

Module 17

Tier 0

Anything that controls identity for everything: DCs, AD FS and signing keys, Entra Connect, AD CS, PAM vault, IdP super-admins, device-management admins. Tier 0 accounts log in only to Tier 0 systems, from PAWs.

Modules 17, 19

Zero Trust, ISPM, ITDR

Zero Trust (NIST 800-207): never trust, always verify, every request. ISPM: finds standing weaknesses (posture). ITDR: detects and responds to active identity attacks. Shared Signals / CAEP: real-time "revoke this session" between systems.

Module 18

Protocol cheat sheets purpose · flow · attacks · detect · defend

NTLM

Legacy Windows challenge-response authentication. Deprecated; NTLMv1 is removed from the newest Windows versions.

Flow
NEGOTIATE → CHALLENGE (random number) → AUTHENTICATE (response computed from the NT hash); the server asks the DC to verify.
Weaknesses
NT hash is as good as the password; no server authentication; no MFA.
Attacks
Pass-the-hash, NTLM relay (with coercion tricks such as PetitPotam), offline cracking.
Detect
4776 NTLM validations where Kerberos is expected; 4624 logon type 3 with NTLM from unusual hosts.
Defend
Audit, then restrict NTLM; SMB signing; LDAP signing and channel binding; EPA; Protected Users group.

Module 8

Kerberos

Ticket-based network authentication through a trusted third party (the KDC on every domain controller).

Flow
AS-REQ (pre-auth) → AS-REP (TGT, sealed with the krbtgt key) → TGS-REQ (for an SPN) → TGS-REP (service ticket, sealed with the service key) → AP-REQ → optional AP-REP (mutual authentication).
Key facts
The PAC carries group memberships; tickets last about 10 hours; clocks must be within 5 minutes; PKINIT adds smart cards and Windows Hello; constrained delegation is OK, unconstrained is dangerous.
Attacks
Kerberoasting, AS-REP roasting, pass-the-ticket, Silver Ticket, Golden Ticket, delegation abuse.
Detect
4769 with RC4 (0x17) across many SPNs; 4768 / 4771 anomalies; TGS without a prior TGT; ticket lifetimes that don't match policy.
Defend
gMSA, AES only, pre-auth on, Credential Guard, Tier 0 isolation, reset krbtgt twice after compromise.

Module 8

SAML 2.0

XML-based browser SSO for enterprise web apps (OASIS, 2005).

Setup
Exchange metadata: IdP entity ID, SSO URL and signing certificate ↔ SP entity ID and ACS URL.
Flow
SP → browser redirect with AuthnRequest → IdP login and MFA → signed SAMLResponse auto-POSTed to the ACS URL → SP session. All front channel.
Assertion
Issuer (≈ iss), NameID (≈ sub), Audience (≈ aud), NotOnOrAfter (≈ exp), AuthnContext (≈ amr/acr), attributes.
SP must check
Signature against the stored IdP certificate, issuer, audience, time window, InResponseTo, destination, replay.
Attacks
Golden SAML (stolen signing key), XML signature wrapping, comment injection, weak validation, certificate-expiry outages.
Detect
App sign-ins with no matching IdP sign-in; signing-certificate changes; AD FS configuration exports.
Defend
HSM or cloud IdP for signing keys; mature libraries; SP-initiated flows; certificate expiry tracking.

Module 11

OAuth 2.0

Delegated authorization for APIs. Not authentication.

Grants
Authorization code + PKCE (user present); client credentials (machine to machine); refresh token; device code; token exchange (on behalf of).
Tokens
Access token (minutes to hours, scoped); refresh token (days to months; very valuable).
Attacks
Consent phishing, device-code phishing, refresh-token theft, redirect-URI manipulation, wrong-audience acceptance, leaked client secrets.
Detect
New high-risk consents (Mail.Read, offline_access); unusual device-code sign-ins; new app secrets.
Defend
Admin consent workflow; PKCE; exact redirect URIs; sender-constrained tokens (DPoP, mTLS); certificates or federation instead of secrets; follow the OAuth Security BCP (RFC 9700).

Module 12

OpenID Connect (OIDC)

Authentication layer on top of OAuth 2.0. Adds the ID token (a JWT).

Flow
Authorization code + PKCE; tokens are fetched over the back channel, server to server.
ID token claims
iss, sub, aud, exp, iat, nonce, amr / acr (how the user authenticated).
Validate
Signature (via the IdP's JWKS), issuer, audience, expiry, nonce.
Remember
A JWT is signed, not encrypted: anyone can read it, so no secrets inside.

Module 12

FIDO2 / WebAuthn / passkeys

Phishing-resistant public-key authentication.

Parts
WebAuthn (browser API, W3C) + CTAP (talks to security keys and phones, FIDO Alliance).
Why it works
The key pair is bound to the website's origin, so the device won't sign for a look-alike site; the server stores only public keys.
Watch
Synced passkeys depend on the security of the cloud account they sync through; recovery flows can reintroduce weak links.

Module 5

TOTP

Time-based one-time passwords (RFC 6238), used by authenticator apps.

How
code = last 6 digits of HMAC(shared secret, time ÷ 30 s). Both sides compute it; nothing is sent.
Weakness
Doesn't know which site it's typed into (relayable); a leaked seed or QR code means codes forever.

Module 5

SCIM 2.0

Standard REST API for provisioning and deprovisioning accounts (RFC 7643 / 7644).

Why
SSO can't remove accounts; SCIM lets the IdP create, update and disable users and groups in apps automatically.

Module 9

Other protocols

RADIUS
VPN, Wi-Fi and network devices; the classic place to add MFA to a VPN.
TACACS+
Admin access to network devices, with command logging.
802.1X / EAP
Network access control; best with device certificates (EAP-TLS).
LDAP bind
An app checks passwords against the directory. Not SSO: the app sees your password.
WS-Federation
Older Microsoft web SSO (AD FS).
SSH
Keys or, better, short-lived SSH certificates.

Module 10

Workload identity (SPIFFE / cloud federation)

Machines prove what they are through their platform, with no stored secret.

Pattern
The platform (GitHub Actions, Kubernetes, a cloud VM) issues a signed token about the workload → it's exchanged for short-lived credentials scoped to exactly that workload.
Examples
AWS IAM roles, Azure managed identities, GCP workload identity federation, GitHub Actions OIDC, SPIFFE / SPIRE SVIDs (X.509 or JWT).

Module 24

MCP authorization

How AI agents (MCP clients) get access to remote tool servers.

Basis
OAuth 2.1; the client discovers the authorization server from the MCP server's protected-resource metadata (RFC 9728).
Rules
Tokens are issued for that specific server (audience / resource indicators, RFC 8707); servers must not pass client tokens through to other APIs.
Local servers
Run with your own permissions: install only trusted ones and keep confirmations on for anything that writes.

Always-alert list

  • Sign-in by a terminated user
  • Honeytoken use
  • Federation or IdP configuration change
  • New Global Admin or super-admin

Incident response playbooks evict, don't just reset

Compromised user account

  1. Block sign-in; revoke sessions and refresh tokens; reset password
  2. Remove persistence: MFA methods, OAuth consents, app passwords, inbox rules, devices, PATs, SSH keys, new accounts
  3. Scope with sign-in and audit logs
  4. Verify the user out-of-band; re-enrol with FIDO2; clean the device
  5. Fix the root cause

Stolen token or session

  • Revoke sessions
  • Find the infostealer; reimage the device
  • Require compliant devices; shorten sessions; token protection

Leaked secret or key

  • Rotate and revoke first
  • Search logs for use of the old key
  • Hunt for other leaks in the same repo or pipeline
  • Verify every copy was rotated (the Cloudflare lesson)

Compromised IdP admin

  • Act from break-glass accounts
  • Check federation, IdP routing, new apps and secrets, policy changes, role grants
  • Revoke all admin sessions

AD domain compromise

  • Assume total compromise; scope quietly
  • Reset krbtgt twice, waiting for replication and ticket expiry in between
  • Reset all privileged and service accounts; check AD CS
  • Possibly rebuild DCs or recover the forest; evict in one coordinated event

Third-party integration breach

  • Revoke the vendor's tokens and keys
  • Review what data it accessed
  • Re-grant with reduced scopes

OEM products real vendor implementations of the concepts above

How an actual product solves what the course teaches abstractly. Sourced from Cisco Live session decks (paraphrased, not quoted at length — licensed conference material). One card per vendor deep-dive.

Cisco Duo: Identity Security (formerly "just MFA")

Duo's own pitch: it evolved from an MFA tool into a full security-first IAM platform — directory, SSO, passwordless, device trust, automation — without replacing a company's existing IdP.

Deployment modes
Three ways to sit in an environment: standalone IAM for companies with no IdP; an identity broker in front of an existing IdP (Entra, Okta, Ping); or an alternate directory just for third parties (contractors, vendors) who shouldn't join the main corporate directory.
True passwordless
Duo Directory removes passwords entirely, including from enrollment and account-recovery flows — the password never exists to begin with, not just "hidden" behind MFA. Works via Duo Directory itself, or synced external directories (Entra, SAML 2.0, on-prem AD). Embedded browsers that don't support WebAuthn get bridged through the Duo Desktop app instead.
Session token theft defense ("Duo Passport")
Strong device binding: the endpoint signs a user+device profile and sends it to Duo's cloud on every app access; if a profile doesn't match what was recorded, the session is treated as suspect. Because the binding is to the device, not just the token, Duo can invalidate a stolen session cookie even after an attacker-in-the-middle (AiTM) phishing attack has already captured it.
Device trust
Two separate checks: device health (disk encryption, firewall, password set, OS version, 3rd-party security agent, browser/plugin versions — a posture check) and trusted endpoints (does this exact device identifier appear in Duo's device inventory at all — a allow-list check, independent of health).
AD Defense — closing the legacy gap
Most legacy on-prem apps only authenticate via Kerberos or NTLM and can't natively support MFA. Duo's AD Defense inserts itself at the domain controller via a subauthentication filter (a DLL) and intercepts successful Kerberos/NTLM logons before granting access, adding MFA to authentication protocols that were never designed to support it. A separate CLI-protection agent does the same for Windows SSH, sFTP and remote PowerShell specifically — the protocols attackers use for lateral movement and privilege escalation.
Provisioning
SCIM both directions: inbound from Okta/Google Directory to build Duo's own user database, outbound from Duo to downstream apps (Secure Access, Webex). This is the practical mechanism behind the course's lifecycle/SCIM material (Module 9) — a real product doing exactly that create/update/delete flow.

Source: Cisco Live BRKSEC-2879, "Duo Identity Security," 2026. See Modules 5 (MFA), 8 (NTLM/Kerberos), 9 (lifecycle/SCIM), 10 (SSO).

Cisco Identity Intelligence (CII, formerly Oort): ITDR and ISPM in practice

The course names ITDR and ISPM as concepts (Module 18) without a concrete product behind them. This is that product — a real implementation of "detect and respond to identity attacks" and "find standing posture weaknesses" as an acquired, shipping tool.

The problem it exists to solve
Most organizations run multiple IdPs at once (Okta, Entra, Duo SSO), each with its own logs and its own partial view. An IdP can only detect what it itself sees — it has no visibility into a different IdP's authentication events for the same user. CII's core pitch is correlation: aggregate authentication events across every IdP into one analytical system, which both surfaces attacks a single IdP would miss and reduces false positives from noisy single-source alerts.
The identity graph
CII builds a graph connecting users, devices, sessions, groups, apps and infrastructure, fed from identity providers, HRIS systems, MDM, and applications — via full inventory sync, delta sync (changed-records-only), or (preferred) near-real-time event streaming. Streaming matters because it's materially faster: a compromised-session detection that's near-instant over streaming can take over 24 hours via periodic API sync — and in that same window, Entra's own alerting can label a real, successful compromise as only "Medium" criticality.
"Checks"
CII's term for a detection rule — explicitly compared to IDS signatures. When collected data matches a check's condition, that check is recorded as failed for that user/account. Checks are tagged to risk frameworks (CIS, NIST, MITRE ATT&CK) and filterable by which IdP they apply to, since not every check works against every provider's data.
Identity Security Posture Management (ISPM) in practice
An organization gets a posture score, benchmarked against similar organizations, tracked as a trend over time — the proactive half of the pitch. Concrete checks it runs: priority accounts (admins) missing MFA, accounts that have never logged in, and tracking real authentication-factor usage against what the organization believes it's enforcing — one quoted example: a CISO certain SMS-based MFA had been fully retired was shown, via the dashboard, that it hadn't been.
Session hijacking detection — a worked AiTM example
The deck walks an Evilginx-style attacker-in-the-middle attack step by step: phishing email → realistic fake Microsoft login page → attacker-controlled proxy captures username, password, and the live MFA-approved session cookie → attacker replays that cookie to access the account, fully bypassing MFA. This is the exact mechanism behind the "stolen session cookie" line in this KB's attack matrix, now with the real product-detection angle: event-streaming from the IdP is what lets CII catch this quickly; without it, detection can take over a day. By default CII runs its checks once daily; "Threat Discovery Mode" can raise that to hourly, but only once streaming and a notification target are configured.
User Trust Level
A single score per user, built from posture, behavior and events over time — explicitly not a real-time risk score, but a longer-horizon approximation other integrated systems (XDR, Secure Access) can act on.
Active Directory specifically
90% of enterprises still run AD. Per Cisco Talos incident-response data cited in the deck, 44% of identity-based attacks specifically target AD — multiple domains, legacy integrations, and generations of accumulated privileged accounts make it a dense attack surface. CII's AD-focused checks include flagging "never logged in" accounts (one customer cleaned up 150 stale AD accounts from this single check) and correlating group membership for privilege-creep detection.

Source: Cisco Live BRKSEC-2162, "Identity Intelligence Demystified," 2026. See Module 18 (ITDR, ISPM) and the attack → detect → defend matrix's session-hijacking entries.

Glossary my own short definitions

AAL / IAL / FAL
NIST assurance levels: authentication, identity proofing, federation.
ACS URL
Where an app receives SAML responses.
AiTM
Phishing proxy that relays login and steals the session.
Bearer token
Works for whoever holds it, like cash.
Break-glass account
Emergency admin; alerts on any use.
CIEM
Cloud entitlement analysis: granted vs used permissions.
Conditional access
Context-based allow, challenge or block at sign-in.
DPoP
Binds a token to a client key so a stolen token alone is useless.
gMSA
AD service account with a long password Windows rotates automatically.
Honeytoken
Fake credential; any use is an alert.
IdP / SP / RP
Identity provider / service provider / relying party.
ISPM / ITDR
Posture management / threat detection and response for identity.
JIT / ZSP
Just-in-time access / zero standing privilege.
krbtgt
The account whose key seals every TGT.
MCP
Model Context Protocol: connects AI agents to tools; OAuth 2.1 for remote servers.
mTLS
Both sides of a connection present certificates.
NHI
Non-human identity: service accounts, keys, tokens, workloads, bots, agents.
NT hash
Unsalted Windows password hash; enough for NTLM (pass-the-hash).
PAC
Group memberships inside a Kerberos ticket.
PAW
Hardened device used only for admin work.
PKCE
Stops stolen OAuth authorization codes being redeemed.
PRT
Entra device sign-in token that gives cloud SSO ("the cloud TGT").
Prompt injection
Hidden instructions in content that hijack what an AI does with its access.
SPN
Service name Kerberos uses to find a service's key.
Tier 0
Assets that control identity for everything else.
UEBA
Behaviour baselining to flag anomalies.
